AWS HOSTING AND DOCKER DEPLOYMENT PLAN
Specification 1.6 | 7 November 2026 | Design only — NOT_DEPLOYED

Decision and timing
Plan Docker now and implement packaging during M2, when the first Streamlit/FastAPI skeleton and dependency lock work. Do not defer containerization to the final demo. Use the same tested image digest on teammates’ laptops, CI and EC2; keep environment-specific data and settings outside images. This documentation update does not authorize writing application code, provisioning AWS resources or deploying containers.
The initial target is one shared EC2 host running Docker Compose, suitable for the capstone demo and a low-volume internal production release after the gates below. Users access a URL, not server accounts. A single host remains a shared failure and resource domain; separate containers do not provide high availability or a strong host-level security boundary. Proposed RPO 24 hours and RTO 4 hours require owner agreement and a measured restore test; they are not achieved guarantees. Use separate EC2 hosts for demo and production when real-data risk or operational ownership requires stronger separation. If the agreed production uptime/recovery target cannot tolerate one-host downtime, choose the ECS/RDS path before that launch.

Runtime and versions
Proposed host: Ubuntu Server 24.04 LTS x86_64, with the exact AWS AMI ID and patched OS build recorded at provisioning. Docker Engine 29.9.3 and Docker Compose plugin 5.7.0 are release-verified candidates; test distribution/architecture compatibility before pinning the host bootstrap. The command is docker compose. Container runtime remains CPython 3.14.10; resolve a maintained base image tag supporting that patch, verify it and pin the image digest at M2. Do not invent a base-image digest. Select and pin the reverse-proxy image tag/digest in the same release manifest. Amazon services have service/API contracts rather than a self-managed package version; record region, resource IDs and IaC revision.
AWS SDK for Python: boto3 1.43.126 is a proposed deployment-only pin for S3/Secrets Manager adapters. requirements-aws-proposed.txt extends core requirements; the local fixture-only path does not require AWS access. A lockfile and smoke tests must cover the AWS dependency set when chosen.
Start sizing assessment at 2 vCPU / 8 GiB (for example an available t3.large) with a separate encrypted gp3 data volume; no GPU is required because inference is hosted elsewhere. This is a demo sizing estimate, not a production throughput promise. Benchmark the actual policy corpus, image sizes and concurrent sessions; budget CPU credits for burstable instances. Record the chosen region, disk capacity/IOPS, concurrent request limit and measured p95 before production. Include ALB, EC2, EBS, snapshots/S3, ECR, NAT/egress, Secrets Manager, CloudWatch, DNS and provider/LangSmith charges in the budget; do not assume the host price is the entire bill.

Initial architecture
Browser -> HTTPS Application Load Balancer with ACM certificate and Cognito/OIDC authentication -> EC2 reverse proxy -> Streamlit UI and private FastAPI containers. Route by hostname to distinct demo and production Compose projects. Use separate project names, Docker networks, secrets, persistent paths, upload buckets/prefixes and LangSmith destinations. Compose profiles alone are not environment or data isolation.
The ALB has subnets in the required two Availability Zones, but the single EC2 target still resides in one zone. Put the host in a private subnet with managed egress to required hosted APIs and AWS services. If network administration chooses a public-subnet host for budget reasons, document that alternative explicitly and retain ingress restrictions; do not silently expose application ports. Only ALB 443 is user-facing; HTTP may redirect to HTTPS. The EC2 security group permits only the ALB security group to the reverse-proxy listener. Do not expose 8000, 8501, database ports, Docker daemon or SSH to the internet. Use Systems Manager Session Manager for administration with the required role, agent and endpoints/egress.
Serve Streamlit at the environment host root and reverse proxy /api/ to FastAPI, removing that prefix if backend routes remain /chat, /sessions, /receipts, /claims/review and /travel/search. Preserve WebSocket upgrade behavior for Streamlit and use request/idle timeouts consistent with the bounded run deadline. Avoid unauthenticated alternate listeners or direct-IP bypass. Health-check exceptions return status only and cannot expose user data.
Authentication must protect UI and API. Verify the signed ALB identity token, expected signer/issuer and expiry; do not trust a caller-supplied identity header. The Streamlit server must forward the verified per-request identity to FastAPI, or use a separately validated short-lived internal identity. The API maps identity to authorized organization/session IDs. An internal service URL is not authorization. Restrict container networks and preserve tenant filtering across caches, state, uploads and RAG. Use a distinct secure authentication session cookie/client for each environment.

Containers and persistent state
Planned artifacts, to be implemented later: separate UI and API Docker build targets, .dockerignore, compose.yaml, a development override, a production override, reverse-proxy configuration, host bootstrap/IaC, deployment/rollback runbook and release manifest. Keep tests/evaluation tooling in a separate test image/target. Runtime images include approved policy and application code, not golden answer keys, .env, raw uploads or dependency caches. No bind mount of live application source, development auto-reload, privileged mode or Docker socket inside app containers. Run as non-root with writable volumes only where needed, resource limits, health checks, restart policy and bounded log rotation.
One API process/worker per environment owns its SQLite checkpoints and persistent Qdrant local index. UI containers must call the API rather than opening those files. Do not start multiple API replicas or rolling overlapping writers against local Qdrant/SQLite. Maintain shared rate limiting within that single API owner. A killed in-flight run may need retry/resume from its last valid checkpoint; test that behavior.
Store checkpoints/session state and vector data in explicit per-environment directories mounted from encrypted EBS, outside container writable layers. Use a separate data volume and documented deletion/replacement behavior; explicitly retain or restore it when replacing the instance. Keep versioned policy artifacts independently so indexes can be rebuilt. Store private uploads in separate access-controlled S3 buckets/prefixes, encrypted with approved keys and public access blocked; an authorized ReceiptStore adapter obtains bytes for the parser. S3 file identifiers must be tenant-scoped and cannot grant arbitrary object access. No public receipt URLs.
Use an EC2 instance profile and temporary AWS credentials rather than static access keys. Restrict ECR/S3/KMS/Secrets Manager permissions. Containers must receive only needed secret values via an authorized adapter or protected runtime mounts; never bake secrets into images/build args/logs. The instance role is a host-level boundary: two Compose projects on one EC2 do not acquire separate IAM isolation automatically. Record this shared-host risk and move production to a separate host or task roles when needed.

Build, release and rollback
After implementation, PR CI runs appropriate deterministic tests, image builds and image/security checks. Documentation CI remains read-only/offline. Publish a commit-tagged immutable image to private ECR, then deploy that digest to demo. Run authenticated smoke checks, verify LangSmith/CloudWatch and inspect the policy version. Promote the same digest to production with approved production configuration; never edit source on the server or deploy a mutable latest tag. Record app commit, base/runtime/proxy image digests, dependency lock, OS/AMI, IaC version and policy/index versions in the release manifest.
Before replacing production containers: prevent new requests, let bounded active runs finish or checkpoint, back up state consistently, validate configuration, then replace the single API writer. Re-establish health before routing traffic back. A Compose restart policy is not an application rollout controller: define how unhealthy containers are detected and replaced. Expect a maintenance interruption on one host; do not promise zero downtime. Keep the previous digest and compatible state snapshot. A schema migration needs a documented backward-compatible or restore-based rollback. Never roll back images blindly after an irreversible state change.
Use GitHub Actions OIDC or an approved equivalent for CI AWS access, and a controlled SSM deployment role. Do not put long-lived AWS keys in repository secrets or give every teammate administrative server access. The repository host can differ; keep IaC and release commands portable. Provision infrastructure through reviewed CloudFormation or another agreed IaC tool; the exact artifact is a later task.

Operations, backup and production entry
CloudWatch covers host/container health, memory/disk, restarts, ALB errors and backup failures. LangSmith covers model/tool traces, active latency, tokens and evaluated quality. Set named on-call/operations ownership, patch cadence, alert recipients, daily provider spend and infrastructure budgets, and receipt cleanup jobs. Redact both logging destinations. A noncritical monitoring export outage must not change claim arithmetic; missed backup/authentication/recovery gates still block a production release.
Default upload retention remains 24 hours. Enforce deletion through an application cleanup job plus S3 lifecycle as a backstop; lifecycle timing alone is not an exact deletion clock. Account for noncurrent versions and incomplete uploads. Exclude raw receipt objects from long-retained database backups unless an approved retention rule permits them. Session metadata backups need their own agreed retention and deletion handling. Expired/missing upload references require safe clarification or re-upload on resume.
Create daily application-consistent backups of SQLite/checkpoints and the policy/index manifest, and encrypted EBS snapshots according to the chosen policy. Do not copy a live SQLite file without its transactional/WAL consistency; quiesce writers or use a supported backup mechanism. Encrypt/restrict backup S3 locations and test restoration to a replacement host with the pinned image. Rebuild vectors from the approved corpus rather than relying only on opaque index snapshots. Test the proposed RPO/RTO under actual data size.
Production gates: authenticated UI/API and cross-session isolation; network bypass prevention; image scanning/patch plan; measured concurrency and error/timeout limits; persistent restart/replacement behavior; successful backup/restore and rollback; monitoring alerts and spending limits; 100 core plus 20 supplemental evaluation with reviewed results; OBS01–OBS06; approved data-retention and actual company policy. Fictional policy 1.1 and demo FX cannot authorize real company reimbursements. If only the fictional policy is loaded, label the hosted service as a capstone/demo even if its infrastructure is production-grade. New policy dates or limits require separate review and tests; golden clocks remain frozen.

Acceptance checks — DEP01–DEP08, all NOT_RUN
DEP01: a fresh checkout builds/runs the pinned UI/API images on the target architecture; the runtime image excludes secrets, private data and golden answer keys.
DEP02: unauthenticated requests and direct backend bypass are rejected; forged/expired identity and cross-tenant sessions cannot read data; authenticated Streamlit WebSocket and API requests work.
DEP03: restarting/replacing a container preserves confirmed state and usable indexes; only one API owns each local data directory; separate demo/prod stacks do not share credentials or state.
DEP04: hosted providers and LangSmith work through allowed egress, credentials rotate without image rebuild and secrets are absent from logs/images; fake canaries verify the checks.
DEP05: restore to a replacement host meets measured agreed RPO/RTO; backups and upload expiration respect retention and private data remains private.
DEP06: roll forward and roll back a versioned release with a documented schema policy; no overlapping state writers, no mutable latest and no unrecorded host edits.
DEP07: load/concurrency, long-running requests, Streamlit connections, rate limits, memory/disk/CPU credits and provider failures stay within agreed thresholds; one-host downtime limits are recorded.
DEP08: CloudWatch/ALB/backup and LangSmith alerts and spend controls are demonstrated; reviewed policy/data classification, golden/OBS evidence and an operations owner are recorded before production access.
These deployment tests supplement the existing golden suite and do not alter its 100/20 counts. Docker images, infrastructure and AWS credentials are not created by this documentation package.

Implementation sequence
M2: validated lockfile, first UI/API, Docker build targets and Compose local smoke tests; start immutable artifact discipline.
M3–M6: keep every workflow runnable through Compose; add tenant-scoped S3 receipt storage, role-based Secrets Manager access, persistence, health endpoints and observability adapters as needed.
M7: push a tested image to ECR, configure reviewed infrastructure and run the authenticated shared AWS demo. An explicit later deployment instruction and approved AWS account/budget are required before resource creation.
M8: complete DEP01–DEP08, restore/rollback/load tests, policy/data review and operational ownership, then promote the exact tested digest to the authorized production environment.
If growth or availability requires multiple replicas, move to ECS (Fargate or EC2 capacity), externalize checkpoints/session state to a suitable PostgreSQL/RDS adapter, run a server/managed vector store and use shared rate limiting. Keep S3 and external secrets. With Streamlit replicas, address WebSocket/session affinity. Revalidate the state/provider adapters and golden tests; an ALB or extra container on a single host alone does not remove the single point of failure. Kubernetes is not required for the initial plan.
